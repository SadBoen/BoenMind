# ADR-0005 万物皆插件:内核只含合同与最小机制

- 状态: accepted-with-conditions
- 日期: 2026-08-28
- 决策类型: 架构裁决(对基线 §17 裁决 R5 的复核结论)
- 来源: Zen consensus 多模型辩论——三个模型家族分任三方并跨裁决轮换角色(AGAINST=gpt-5.6-luna, EMPIRICAL=gemini-3.7-flash, FOR=glm-5-turbo);两轮(独立立场→交叉质证)+逐裁决合成
- 辩论记录: `architecture/debates/R5-everything-is-plugin-transcript.md`
- 辩论数据: 共识 9 项 / 未决分歧 4 项 / 条件 6 项 / 决策要点 8 项;合成结论 **amend**

## 背景(原裁决文本)

> 内核只由合同与最小机制组成;模型连接器、记忆引擎、定时器、评价器、Secret Store 都是扩展点上的普通 Provider,不是内核特权组件;新增功能默认走插件路径,只有既有扩展点无法表达才允许改合同,并按 §13.5 升级级别处理。

## 裁决(决策要点)

1. 内核只由合同与封闭清单化的最小机制组成：Capability 裁决、引导信任根、持久事件日志单写者与 event_seq、双代际写入租约与栅栏、Operation/Approval 状态机、L0 监督单调时钟；新增任何内建机制必须逐项通过安全不变量四判据（写全局权威状态、需单调可信时间或全局序列、参与启动信任根或凭据版本、须与 Operation 结果原子提交）并给出「为何不可做成 Provider」的证明，清单变更按 §13.5 处理。
2. 模型连接器实现、可重建记忆索引、评价器、业务定时器（Cron/提醒/计划任务）默认以普通 Provider 身份注册于扩展点，新增功能默认走插件路径，不设内核特权实现；「万物」指功能能力层，不含底层存活与不变量机制。
3. 安全不变量由内核最小机制强制执行，Provider 只是租约持有者与合同履行者，不得自行决定写入协议、提交栅栏、可信时间与恢复语义；恢复以语义连续为目标（行1263），outcome_unknown 一律先核验外部系统、不自动重放。
4. L0 监督时钟与业务定时严格分层：监督 watchdog 与 L2 Operation 超时为内核内建单调时钟机制、不依赖外部 IPC、不可插拔；业务定时能力为可替换 Timer Provider，二者禁止混同表述。
5. Secret 存取采用「内核 Secret Broker 最小机制＋可替换 Secret Engine Provider」两层结构：内核持有根密钥引用、会话凭据版本锁与凭据版本栅栏；引擎 Provider 的热替换合同必须内置凭据同步握手、版本租约转移与审计日志连续性语义，不满足者由内核栅栏拒绝切换。
6. 改合同实行双重门槛：表达性测试（既有扩展点语法不可表达）与不变量保持测试（包装为 broker.call 后仍无法维持全局序列、可信时间、凭据版本、恢复语义）须同时成立，方按 §13.5 升级级别处理；不得以「可包装为 broker.call」拒绝必要的合同演进，也不得以包装规避不变量归内核。
7. 无特权通道为强制纪律：第一方与第三方组件同等经 manifest 声明＋Broker 裁决，Execution Log 不存在不可记录、不可回放的调用路径；举证责任恒在「增加特权」一方，交付压力下绕过举证义务须作为 §13.5 级事件留痕并触发架构评审。
8. 阶段一进程内实现必须第一天按 Provider 边界设计，并以 M3（模型连接器外置为独立进程、调用方与记账零感知）、M7（签名从来源标识升级为完整性验证）及「跨代热替换经写入栅栏证明无未决 outcome_unknown 孤儿副作用」为可证伪验收；任一未通过即复审对应能力的 Provider 化判定，阶段二迁移因此降为部署拓扑变更而非 Major 级系统升级。

## 条件与验收

- 内核最小机制实行封闭清单管理（Capability 裁决、引导信任根、事件日志单写者与 event_seq、代际写入租约与栅栏、Operation/Approval 状态机、L0 监督单调时钟），新增项必须逐项通过安全不变量四判据并留有「为何不可做成 Provider/App」的书面证明；清单变更按 §13.5 升级级别处理。
- 承载安全语义的 Provider 设置注册门槛：其合同必须内置健康检查、超时、轮换、凭据版本与 outcome_unknown 外部核验/对账语义（KMS v1 教训），缺任一项不得注册生效。
- 行197 举证义务制度化执行：每次内核增长留痕可审计，交付压力下不得绕过；任何事实松绑（绕过 Broker 的内部通道、未走 §13.5 的合同变更）须作为 §13.5 级事件记录并触发架构评审。
- M3/M7 可证伪验收按时执行：M3 模型连接器从 L2 进程内迁出为独立 Provider 且调用方与记账零感知；M7 签名从来源标识升级为完整性验证；跨代热替换（§13.4）须以写入栅栏证明未产生未决 outcome_unknown 孤儿副作用——任一未通过即触发「纯 Provider 模型不足以支撑该关键服务」的裁决复审。
- 记忆引擎 Provider 只能实现为可从权威事件日志重放重建的下游索引，不得持久持有唯一真相；其崩溃与热替换的恢复路径定义为日志重放。
- 合同演进治理常态化：L1 演进全部走 §13.5、可回滚、原因可追溯至双重测试的证明；预期首年至少一次 Minor 演进，若零演进须审查扩展点是否被教条压制。

## 共识(经质证未被驳倒的命题)

- 内核＝合同＋最小机制的分层结构（小内核、稳定合同、进程边界崩溃隔离、Runtime generation 验证→切换→排空→回滚）经两轮质证成立：Erlang/OTP、Kubernetes（CRD/CRI/CSI/KMS）、Chromium servicification、VS Code、systemd 五个独立谱系收敛于同一形态，且基线 §12.1 行1121 自证进程内组件不能独立崩溃恢复——故障域必须收缩到单个 Provider 进程、由 Supervisor 按规则重启，持久 Task/Operation 状态不陪葬。FOR 与 AGAINST-R2 在「实现默认 Provider 化＋进程隔离」上已无分歧。
- 全局不变量由内核最小机制强制执行、Provider 只是租约持有者与合同履行者：持久事件日志 L2 单写者追加与 event_seq 全局单调（§8.3 行739）、双代际写入栅栏与单写者租约（§13.4 行1260）、Operation/Approval 状态机及 succeeded/failed/outcome_unknown 三分恢复语义（§13.3 行1205-1219）不得由普通 Provider 自行决定。——AGAINST 提出，EMPIRICAL-R2 明确接受「权威状态机、安全栅栏、根信任引导与监督时钟归内核控制面」，FOR-R2 论证此即 R5 的合同＋最小机制，三方在机制归属上收敛。
- L0 监督机制与业务定时分层：L0 Supervisor watchdog 与 L2 Operation 超时属内核内建单调时钟最小机制（不依赖外部 IPC、不可插拔，§12.1 行1123），业务 Cron/提醒/计划任务是可替换 Timer Provider（§9 行650 的「定时能力」仅指后者）。——EMPIRICAL 提出、FOR 接受，AGAINST 的系统休眠/插件卡死反例据此消解（行739 已内置单调＋UTC 双记与唤醒重算）；基线行125「万物皆插件不是要求 L0/L1 任意热插拔」为该分层提供文本依据。
- 启动信任根是最小机制而非 Provider：引导身份验证、Broker 初始裁决策略、root key 存储属内核最小机制；Secret Store Provider 管理的是 Agent/用户层凭据（模型 API key、第三方 token），与内核自身引导信任根分层（与 K8s API server 自带 TLS 证书同构）。——FOR 提出该分层后，AGAINST 的鸡生蛋质疑与 EMPIRICAL 的「L0/L1 静态内建引导根」要求被同时吸收，未被驳倒。
- 安全能力可插件化的成立条件是合同充分性而非特权身份：K8s KMS v1 因缺密钥身份/健康检查/轮换语义于 1.28 废弃、v2 补齐 gRPC 合同后成熟；Vault barrier storage 归核心、Secret Engine 为带明确合同的插件。——三方据此一致认定：承载安全语义的 Provider 必须在合同中内置健康检查、超时、轮换、版本语义方可注册；AGAINST 的凭据版本错乱剧本被定性为合同不足问题，其修复方向是强化合同而非提升特权。
- 「无特权通道」（manifest 声明＋Broker 裁决，行191）作为能力安全与全链路可审计性（Execution Log＋收据＋审批回放，行516-533）的治理纪律被三方接受保留：任何特权通道都会在 Execution Log 中制造不可记录、不可回放的调用路径。三方同时确认该纪律严格性超出全部主要先例（VS Code proposed API、K8s static pod、systemd 内部 API、Chromium 特权 Mojo Broker），其健康判据是「合同变更全部走 §13.5 且可回滚」而非「合同永不改」。
- 行197「先证明该抽象无法用既有扩展点表达」的纯语法测试被三方一致判定不足：任何功能都可包装为 broker.call，必须补充「不变量保持」维度——检验表达后的版本能否维持全局序列、可信时间、凭据版本、恢复语义。三方在「测试须双维化」上无分歧（残余分歧仅在判据的载体归属，见 disputes）。
- 阶段一→阶段二迁移压缩机制成立：§5.4 行536（进程内实现＋第一天按 Provider 边界设计）＋§21 行1838（原样迁移为独立进程 Provider）使两阶段共享同一合同面、只差部署拓扑，避免 §13.5 Major 级不兼容迁移；配套可证伪验收（M3 连接器换出零改动、M7 签名升级为完整性验证）被三方共同接受，并认定行536 与行1159（签名仅来源标识）为可预见的实证债务。
- 记忆引擎的界定澄清成立：L2 Core 独占权威事件日志与 Operation 状态机（§2.2 行136 将「记忆索引」归 L2 状态），作为 Provider 的记忆引擎仅为下游可重建检索索引，崩溃或热替换通过从权威日志重放恢复，不承载持久一致性。——EMPIRICAL-R2 提出，消解 §2.1 行105 与 §2.3 行179 的部分表面矛盾。

## 未决分歧(如实记录,不强行抹平)

- 不变量执行载体的表述归属：AGAINST-R2 坚持「受保护控制面」须作为独立于合同的架构范畴写入裁决——Secret Store、Event Store、权威 Scheduler 即使实现外置，其写权限、版本租约、事务边界、恢复证明归内核控制面所有，此类 Provider 的替换须走冻结写入→租约转移→状态等价校验的受控提交协议，普通 §13.1 的 draining＋原子换绑不足以安全替换它们；FOR-R2 坚持这已由「合同＋最小机制」覆盖（行191 裁决面、行1260 租约与栅栏、行1205 三分语义），并主张另设「特权身份」会把安全保证从可审计的合同规则退化为「因为它是内核组件所以可信」的隐式假设。双方对「机制必须归内核」无分歧，但对是否需在合同之外单列控制面所有权范畴未收敛；AGAINST 未回应 FOR 的「你的分层提案即 R5 的精确描述」论证。
- 凭据版本裁决权的归属：EMPIRICAL-R2 与 AGAINST 要求 Secret Broker 核心持有根密钥引用与会话凭据版本锁、凭据版本 fence token 由内核强制（版本裁决权不可下放插件）；FOR 认为凭据同步握手＋版本租约转移属 Secret Store Provider 的合同义务、经 §13.5 补合同即可，内核只持有自身引导 root key。「凭据版本栅栏是内核强制机制」还是「Provider 合同义务＋内核校验」两轮后未合并为同一机制表述——此分歧直接决定 AGAINST 所述 draining 窗口凭据错乱剧本由哪一层负责防御。
- 权威 Scheduler 与可信 deadline 的归属悬置：AGAINST 四判据将「需要单调可信时间或全局序列」的权威调度列为受保护控制面；EMPIRICAL 仅裁定监督时钟归 L0/L2、业务定时归 Provider，对「业务调度的截止时间/重试/审批是否构成需内核可信 deadline 背书的跨 Task 安全语义」未表态；FOR 未正面回应该论证。基线行1005 将截止时间列为 L2 规范状态、行650 又称内核不持有调度特权，该文本冲突在本轮未被裁决。
- 「零特权通道」的长期可持续性张力：EMPIRICAL 维持「无先例的激进治理纪律，应预期在真实需求压力下被打破或事实上松绑」的基率判断；FOR 以单用户可审计威胁模型辩护其正当性，并承认若行197 制度化审查在交付压力下被绕过、安全收益将迅速消散。规范层面三方均同意保留，经验层面「能否长期执行」不可判定——只能以可证伪验收与制度条件约束，而非消除。
