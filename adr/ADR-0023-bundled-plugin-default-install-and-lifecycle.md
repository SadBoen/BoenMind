# ADR-0023: 官方随包插件默认安装与生命周期管控

- 状态: Accepted(用户 2026-09-06 六点意见裁决)
- 日期: 2026-09-06
- 关联: ADR-0005(能力提供方=插件)、ADR-0006(权限以合同显式化)、ADR-0017(MCP 治理)、ADR-0011(App=stdio MCP)、ADR-0019(壳子执行面)
- 背景: 用户在 VPS 升级 v0.0.9 后提出插件管控六点意见(本 ADR 逐条落地):①批准接入后自动热重载(热重载按钮保留作保险)②批准后清单自动刷新 ③探活指示灯保留、手动「测试」按钮删除 ④操作列改为「编辑/配置/卸载/删除」(删除=物理删除原文件+警告栏) ⑤官方不再随包的存量插件标记「建议删除」 ⑥官方随包插件默认安装。此前两段式「扫描→显式批准=安装」(ADR-0005/0006/0017)对官方随包件与第三方件一视同仁,导致每次升级后官方插件都处于「文件已在、等用户批准」的悬置态——用户必须手动发现、手动批准,与其对官方件的信任预期(官方件与主程序同包同源=同等信任级)不符。

## 决策

### 1. 官方随包插件默认安装(启动播种)

服务器启动时,在 MCP 统一装载(sync_from_config)之前扫描官方随包目录(exe 同级 `plugins/`),对「mcp.json 未登记 且 不在墓碑名单」的候选按批准接入完全相同的形状(--self-describe → 合同 schema 校验 → mcp.json + manifests 双写)自动落盘,随后随统一装载一次上线。

信任论据:官方随包插件与主程序二进制同一发布包、同一分发渠道、同一信任级——主程序本身就以该插件 exe 的形态执行代码,默认安装不扩大任何信任边界。这与 VS Code 内置扩展、浏览器内置组件同款模型。**用户主权**:本决策由用户 2026-09-06 明示(「官方最新带的插件,建议默认安装」),构成对 ADR-0005/0006/0017「显式批准=安装」在**官方随包件**范围内的修订;**第三方件(数据目录 `mcp/` 手动放置)不受影响,仍走扫描→显式批准**。

### 2. 墓碑:用户「不要」的持久留痕

默认安装引入「复活」风险(卸载后重启即回),以墓碑文件化解:`<data>/config/mcp-removed.json`(私有管理文件,不入合同)。规则:

| 动作 | 墓碑 |
|---|---|
| 卸载官方随包来源插件 | 写入(重启播种永不复活) |
| 卸载数据目录来源插件 | 不写(用户手动放置=安装意图,仍可再批准) |
| 删除(purge,任何来源) | 一律写入 |
| 显式批准接入 | **清除**(恢复安装的唯一正路) |

先例:web_multisearch 的 providers 配置已有 `deleted` 墓碑抑制内置回填(同构语义)。

### 3. 批准即上线;卸载即下线

- **批准接入**(POST /admin/mcp/approve)落盘后同请求内自动热重载(与「重载 MCP」同一 sync_from_config 收口,helper `run_mcp_sync`),响应带上线结果(工具数/失败明细);显式批准同时清墓碑。热重载按钮保留作手动保险。
- **卸载**(DELETE /admin/mcp/{name})落盘后即时热下线(摘除项 disconnect+unregister,ChildKill 兜底杀子进程),不再要求用户手动按「重载 MCP」。
- 前端批准链路不再重复调 reload(避免全量同步双跑)。

### 4. 删除 = 卸载 + 物理删除原文件

新端点 POST /admin/mcp/{name}/purge:摘配置 → 停进程 → 删文件(插件 exe + manifests/\<name\>.manifest.json + config/mcp-\<name\>.json)→ 写墓碑。Windows 下运行中的 exe 删不掉但可改名,复用升级链路的 rename-aside(`.old-<ts>` 让位)兜底并如实报告。前端以警告栏(非原生 confirm)列出将删清单,二次确认。**边界**:官方随包件被 purge 后,未来升级仍会重新投放文件(合并覆盖语义),墓碑保证其保持停用——文件在场≠在役。

### 5. 弃用标记:官方已不随包的存量插件

release 工作流把仓内清单 `plugins/official-plugins.json`(随包插件**声明名**,非 exe 文件名)复制进包内 `plugins/.official.json`;升级换装随 plugins/ 合并落地。服务端 mcp_list 对每个在役插件推断来源(command 前缀=bundled/data)并给出 `deprecated` 标记:bundled 来源且不在官方清单 → 前端显示「已不随包」徽标(建议删除),不自动删。清单文件缺失(旧版安装/本地开发)→ 不标记,优雅降级。**不引入 mcp.json source 字段**(合同 additionalProperties:false,来源由 command 路径前缀可靠推断,零合同变更)。

### 6. 探活面收敛

行首绿点(连通性指示灯)保留,30s 自动探活不变;手动「测试」按钮与 `api.mcp.test` 前端方法删除(与自动探活同源冗余);后端 `/admin/mcp/test` 端点保留(管理面 API 兼容)。

## 后果

- 合同零变更(管理面字段 origin/deprecated/tombstoned 不入册;mcp.json schema 不动)。
- fresh install 开箱即得官方插件;在线升级用户的新官方插件零点击上线(本次 VPS context_inspector 悬置态的直接解法)。
- 用户对官方件的控制权完整保留:卸载=停用+不复活;删除=文件级清除+永不复活;批准恢复=一键回滚上述两者。
