## 3. 存储引擎调研结论（已拍板：**不切换**，记录备查）

用户本轮问了"官方核心用没用 sqlite"+"切换上次用的 Rust 版 sqlite"，已完整调研实测：

- **官方核心主存储是 JSONL**（`packages/bundle/web-app/cordis.patch.yml`：storage-json +
  session-persistence-jsonl，zstd 压缩）。官方 sqlite 只用在两处：`session-query-sqlite`
  （全文搜索索引，`node:sqlite` 即标准 SQLite C，**不是 turso**）和可选 `storage-sqlite` KV。
- **legacy/pi-kernel 分支的 bm-storage-turso 用的 turso 0.7.2 = limbo 的 Rust 绑定**
  （turso_core 就是纯 Rust 引擎；libSQL 是另一个 C fork，别混）。最新 0.8.0-pre.4
  （2026-08-11，limbo 当前版）。
- **本机实测**（同 events 表同 SQL，release）：rusqlite 141.5 万行/s 插入 / 41.8 万次/s
  点查；limbo 16.7 万行/s / 7.5 万次/s——**慢 8.5x/5.6x**。
- **limbo 探针实测**：WAL/synchronous=FULL/foreign_keys/busy_timeout 全部可用（WAL 须用
  query 读，execute 报 unexpected row）；向量 ✅（vector32 + vector_distance_cos 实测正确）；
  **中文 FTS ❌**（'BoenMind' 命中、'心智平台'/'平台'/'完全' 全 0 命中——tantivy 默认分词
  切不了中文）；FTS 属 experimental 须 `experimental_index_method(true)` 开关、`USING fts`
  是 limbo 特有语法（FTS5 不兼容）。
- **拍板**：内核存储底座保持 rusqlite。limbo 的价值在向量+tantivy 搜索，将来做独立搜索/
  向量库或等 1.0 + 中文分词接好再评估（旁挂引擎，不动事件日志底座）。

## 4. 下轮主线 A：P0 三项（逐项实现要点）

P0 都是**内核 wire 行为**（不属于插件），按依赖序做。做完每项跑 §2 验证矩阵。

### P0-1 错误归一化 normalizeLlmFailure（对齐 `llm/tests/adapter-failure.spec.ts` + `service.spec.ts`）

现状：`kernel-contracts::LlmError` 只有 `{message}`（`kernel/kernel-contracts/src/error.rs:79`）；
finish 错误码散落在各处字符串。DSH 要求：
- adapter 任意拒绝（非 Error、恶意 coercion、访问器字段、畸形 failure 快照）→ 终态
  `{message, code:'UNKNOWN'}`；
- 结构化 LlmError `{message, code, status, providerRetryAfterMs, requestId}` **原样入终态**。

实现要点：
1. `kernel-contracts` 的 LlmError 加可选字段：`code: Option<String>`、`status: Option<u16>`、
   `provider_retry_after_ms: Option<u64>`、`request_id: Option<String>`（serde 缺省 None 不
   破坏现有构造）。
2. openai.rs 的 HTTP 错误分支（`stream_inner` 非 2xx 处）构造 LlmError 时带齐
   `code`（map_http_code 已有）、`status`、`request_id`（读 `x-request-id` 头，回退
   `x-deepseek-request-id`）、`provider_retry_after_ms`（读 `retry-after` 头，秒数或 HTTP
   date；0/非法/过去 → 省略）。
3. `FinishReason::Error` 是否扩展字段——看 loop 消费处（`kernel-loop/src/lib.rs:402`
   finish Error 分支）现在只取 message+code。**最小改法**：LlmError 结构化字段只在内核
   错误路径保留，wire 上仍 `{message, code}`；若要对齐 spec 的 `{status, requestId}` 上
   wire，则 FinishReason::Error 加 `extra: Option<Value>` 透传（先做内核层，wire 透传
   标记为 P1 再看）。
4. 单测镜像 `adapter-failure.spec.ts`：恶意 coercion/访问器字段的归一化路径（Rust 侧用
   `catch_unwind` 或对 `String::from` 的错误做 sanitize 函数 + 单测）。

### P0-2 上下文超限/配额内容分类（对齐 `adapter.spec.ts` HTTP 分类用例）

现状：`openai.rs::map_http_code` 只按状态码分类。DSH 要求：
- 400 + body 匹配上下文超限模式（`context_length_exceeded`、`context-window-overflowed`、
  `This model maximum context length is 128000 tokens`、`input is too long for this model`、
  `request too large for model context`、`input exceeds the model context window limit`）
  → `CONTEXT_WINDOW_EXCEEDED`；
- 429 + `insufficient_quota`/`account balance depleted`/`usage-limit-exceeded`/`out of credits`
  → `QUOTA_EXCEEDED`；429 + `rate limit` 类 → RATE_LIMIT；
- **413 状态优先**（内容分类不覆盖 413 → HTTP_413）。

实现要点：`map_http_code(status, body)` 内加内容匹配（`extract_api_error` 已有 message
提取，对 message 做关键词匹配，镜像 `service.spec.ts` 的 `classifyOverflow/classifyQuota`
判词清单——判词表在上轮盘点 §service.spec.ts 有完整列表）。单测镜像两条 each 用例。

### P0-3 abort 语义（kernel-loop cancel 端口，对齐 `adapter.spec.ts` abort 用例）

现状：`session.cancel` 是空实现（api.rs 注释"M1：无取消实现"）；kernel-loop 无 cancel 端口；
`FinishReason::Cancelled` 只在模型侧主动产出时被消费。DSH 要求：请求 signal abort → 终态
`finish{kind:'aborted', failure:{code:'ABORTED'}}` 且**仅此一个 chunk**；预 abort 不碰传输；
中止穿透 resolveModel 与 fetch。

实现要点（这是本轮最大的一块，至少半天）：
1. `GenerateOptions` 加 `signal: Option<Arc<AbortSignal>>`（kernel-contracts 自定义最小
   AbortSignal：`Arc<AtomicBool>` + 订阅回调，避免引 tokio-util 全家桶）。
2. openai.rs `stream_inner`：循环里查 signal.is_aborted() → yield
   `Finish(Cancelled)`（或 Error{ABORTED}）+ return；`.send()` 前预查。
3. `MultiProviderLlm::stream` 透传。
4. web-server `session.cancel`：找到 running session → 触发其 agent 的 abort 信号（
   ReactLoopAgent 加 `abort()` 方法，存信号引用）。
5. loop 消费 `FinishReason::Cancelled` → `TurnEndReason::Aborted`（现在归 Error{ABORTED}，
   对齐 DSH 是 `aborted` 独立 reason 词汇）。
6. 单测镜像：预 abort → 只一个 finish chunk；流中 abort → 恰一个 chunk。
