## 一、结论摘要

1. **构思成立，方向无硬伤**。三条铁律之间没有内在矛盾（论证见 §二）；事件日志底座（三维寻址 / ignorable 守卫 / replace 遮蔽 / 投影重放）在 Life Agent OS 与 dsh 两家里都有源码级同款语义——我们不是拍脑袋，是复刻了被验证过的姿势；"事件日志唯一事实源 + 应用插件 + Steward"的组合在赛道内仍无完整同款。
2. **代码质量过关，诚实性做得比对手好**。173 测试选择性全绿、四新 crate clippy 零警告、契约层零依赖纯净、partial 标注诚实（ToolResult.output/subscribe/删除联动都明说了没做）——kernel.chat"宣称与交付脱节"的坑没有踩。几个小脱节见 §三·19-23。
3. **发现 1 个真崩溃一致性缺陷（单条 append 非事务）+ 2 个长会话性能问题（N+1 读、O(n²) turn 计数）+ 一批接口形状待定项**——详见 §三。都是阶段 1 可低成本修的小件，**不构成推翻设计的理由**。
4. **最大的诚实性缺口：双写是"事后重构"，不是执行流**。现在事件日志记录的是"消息面级事实"（谁说了什么），不是"执行级事实"（第几步调了什么、输出是什么、压缩发生在哪）——事件顺序/step 号是收尾时拼的、ToolResult.output 是空串、chunk 不落、压缩事件没接线。**agent-loop 移植是补全的唯一路径**，立项顺序上它应先于 pi-compat（见 §五拍板点 1）。
5. **缺一件 dsh 有而我们没有的地基：事件格式版本化**。ignorable 守卫只防"旧版本读新事件类型"，不防"信封结构演进"（字段改型/语义变化）。dsh 的 `SESSION_FORMAT_VERSION` + 迁移链（"能解析 ≠ 语义正确"）是我们的空白。趁日志数据还少，**现在加成本最低**（§五拍板点 3）。

## 二、审构思（①号任务：查逻辑漏洞）

### 2.1 三条铁律之间有矛盾吗？——没有

- 铁律 1（用户空间寄生）管"向下"：Agent OS 永远站在宿主 OS 肩膀上，不碰裸机——与铁律 2/3 无交集，无张力。
- 铁律 2（会话即生命周期、Agent 自主决策）管"横向"：会话边界是 Agent 的工具集而非系统强加。与铁律 3（吸收不进核心）唯一可能的拉扯点是：会话管理工具（session.fork/archive）算不算内核？架构已答：**日志原语在内核（fork 是日志语义），会话决策在 Agent/Steward**——分层正确。
- 唯一值得盯的张力（非矛盾）：铁律 3 要求内核最小，但"模型可见即已记录"不变量要求**每个新模型可见输入都新增 CoreEvent 变体**。17 个变体会随 agent-loop 移植、压缩引擎升级持续膨胀，而膨胀点集中在"准内核"（agent-loop）。dsh 用 TS 声明合并解决，Rust 没有——所以要么 CoreEvent 继续长大（契约层必须版本化，呼应结论 5），要么过早下沉 Custom 失去强类型。**这不是现在的问题，是"为什么必须现在加版本化"的另一个理由。**

### 2.2 事件日志作为统一底座——四个边界复核

| 边界 | 复核结论 |
|---|---|
| 多进程写 | 首版不承诺是**对的**（单写者 Mutex + UNIQUE 兜底，冲突会报错而非静默坏）。真多进程是阶段 3 RPC 代理写的事；append-only 天然无冲突，只要 seq 分配单点化（主设备分配、其他设备代理写），跨设备同步架构上是通的——预留正确 |
| 跨设备同步 | 同上，但注意：同步 ≠ 只代理写，还要决定"谁是 seq 分配者"——建议记为阶段 3 的租约问题，现在不设计 |
| 会话删除 | 现在是孤儿数据（partial 已标注）。**隐私角度这是唯一该提前的**：用户删会话 = 期望数据没了，event_log 留着等于没删干净。拍板点 5 |
| 日志膨胀 | 磁盘不是问题（30 轮 180 事件，一年几十 MB 级；SQLite 扛几百万行）。**先疼的是读路径**：全量 replay + 每行一条 SELECT（§三·2）。压缩只压消息面不压日志——这是设计（append-only 全量事实），但投影 checkpoint（`Projection::checkpoint` 已有接口、无持久化）该在会话打开时做增量恢复，而不是每次全量 fold |

### 2.3 时间哲学（实现速度∝Token、M5 自举）站得住吗？——站得住，有一个落地张力

- "地基期人力密集、爆发期 token 并行"的判断正确：阶段 0-3 的决策是串行的（这次复核就是证据——内核决策一个接一个，没法并行）。
- 隐含假设：**100 小弟共享同一个事件日志不会互相踩**。落到存储层：turso 单连接 Mutex 串行**全部读写（read 也持锁）**——并行度上限 = 单写者吞吐。现在完全不疼（append 是 µs 级、读路径暂无消费者），但到"多 agent 阶段"读路径（每个 agent 每步投影）必须出锁或分连接。**记为实现期调优，不拦路**。
- "大窗口假设"复核：战略文档的结论（大窗口是压缩的放大器不是替代品）维持。1M 上下文让"日志重建到模型"的成本下降，但审计/回放/多 agent 共享/成本-注意力价值不降。

### 2.4 路线图优先级——合理，三处可提前

| 建议提前的事 | 理由 | 时机 |
|---|---|---|
| 事件格式版本化 | 数据量小改 schema 最便宜；这是所有后续演进的保险丝 | 阶段 1 开头 |
| Port 注册表形状定案 | 14 个 Port 都走 `Arc<dyn>`，而 Any 注册表存不了 trait object（交接已查证事实 2）——现在只有 event_store 一个特例，等 Port 多了再改就是全仓 breaking | 阶段 1 开头（§三·10） |
| 压缩事件接线 | 现有 ctx-compactor 的调用点挂 CompactionStart/Summary/End 事件即可，低成本补上"压缩可审计" | agent-loop 移植早期 |

没有发现"更早该做的地基"被遗漏——事件日志先行是对的（它是两条主线的共同底座）。

## 三、查漏补缺（③号任务：代码级发现清单）

> 行号以当前 main（8485250）为准。严重度：🔴=会造成数据层故障 🔶=真实使用会先疼 🟡=接口形状/一致性，现在定便宜。

### 3.1 崩溃一致性

- **🔶 单条 append 非事务**（`bm-storage-turso/src/event_log.rs:216-219`）：INSERT 事件与 upsert_head 是两条独立语句。若两步之间崩溃 → head 落后 → 该分支下次 append 必撞 UNIQUE → **该分支日志永久卡死**。`append_batch` 有 BEGIN/COMMIT，单条没有，不一致。且 `checkpoint.rs::recover()` 只 mark_clean、不修 head，无自愈。**修法：单条 append 并入事务（或统一走 batch），recover 时从 `max(seq)` 重建 branch_heads。**
- 🟡 死代码（`event_log.rs:210-212`）：`if head == Some(next)` 恒假（next 恒 = head+1），SeqDuplicate 检查形同虚设（实际兜底靠 UNIQUE）。清理或让检查有意义。

### 3.2 性能（踩在"30 轮长对话/多会话"真实使用模式上）

- **🔶 N+1 读**（`event_log.rs:129-163, 388-389`）：read 每行事件重新 prepare + SELECT 一次 data 列。30 轮 180 次查询，500 轮上万次。修法：主查询直接带 data 列（8 分支 SQL 里加一列）。
- **🔶 O(n²) turn 计数**（`bm-server/src/chat.rs:395-401`）：每个 prompt 全量 replay 数 TurnStart。会话越长每轮越慢。修法：SQL COUNT 或内存缓存 head turn。
- 两者叠加正好命中用户最常用场景（长对话），建议阶段 1 一起修。

### 3.3 语义缺口（双写的"事后重构"性质）

- 🟡 **事件顺序/step 是收尾拼的**（`chat.rs:604-669`）：真实执行是 assistant 文本流 → 工具执行 → 结果 → 继续，双写落的是 [ToolCall₁, ToolResult₁, …, AssistantMessage, TurnEnd] 收尾 batch。投影靠占位合并修好了消息面（交接事实 7），但日志本身的 step/turn 语义是近似值。**agent-loop 移植才有真序。**
- 🟡 **压缩事件没接线**：现有 ctx-compactor 的压缩动作不产生 CompactionStart/Summary/End 事件 → 长对话被压缩后，模型上下文已换摘要、事件日志消息面仍全量，**两个事实源漂移**。partial 标注里没有这一条，建议补上（比 ToolResult.output 更值得标注）。
- 🟡 **TurnEndReason 只有三态**（Completed/Failed/Cancelled，`bm-protocol/src/event.rs:67-71`）：架构文档 5.1 承诺的"未闭合 turn 打 interrupted 标记"（dsh 语义）没实现——checkpoint_state 全局单行是弱化版，恢复时无法区分"正常结束"与"turn 中途崩"。Steward/会话生命周期（阶段 5）需要这个信号，建议阶段 1 补 Interrupted + 启动时对未闭合 turn 补写。
- 🟡 **request/header 无 prompt 快照**（`event.rs:87-91` 只有 provider/model/created_at）：system prompt、工具 schema、skill 注入都影响模型输出，但日志查不到"模型当时看到了什么"。这是"可审计的心智"护城河缺的一角，dsh 的 request/header 记录规范化配置。建议阶段 1-2 补（可先只落 hash）。
- 🟡 **chunk 不落日志**：双写只写最终 AssistantMessage，无逐块回放保真（dsh 逐块保留 + 字节一致测试）。partial 应标注。

### 3.4 接口形状（现在定便宜，晚了是 breaking change）

- 🟡 **Any 注册表存不了 trait object**（事实 2 的后果面）：A2 的 14 个 Port 全走 `Arc<dyn>`，现在只有 event_store 特例。**建议阶段 1 开头用 `struct PortBox<T: ?Sized>(Arc<T>)` 包装**（Sized，可进 Any，downcast 后解出 `Arc<dyn T>`，零 unsafe）——一劳永逸解决全部 Port。
- 🟡 **Loader 无"等待就绪"**（`loader.rs:65-75`）：deps 不满足直接失败，安装顺序 = 手工编排。架构承诺的"依赖表达、不手工编排"（D1）只兑现一半。dsh 的 inject 是等就绪再启动。QuickJS 引擎插件 + 依赖它的应用插件会出现真实顺序问题——阶段 1 定：deferred 插件（等就绪）or 接受有序安装。
- 🟡 **plugin 实例 apply 后即 drop，且无 per-plugin disposer 分组**：卸载特定插件不可行（升级/热更新的前置）。QuickJS 运行时可以服务化存活（Arc 注册服务），但"卸载"需要 per-plugin 分组（`Kernel::install_plugin` 现在全部塞全局 vec）。
- 🟡 `install_plugin` 用 `try_lock().expect()`（`lib.rs:165`）：两个任务并发装插件 → panic 而非等待。低概率，改 `.lock().await` 即可。

### 3.5 一致性小件

- 🟡 `Disposer::join_all` 正序 fire vs Kernel 级逆序（卸载逆序 = 后注册先撤销的纪律不一致，`plugin.rs:31-38`）。
- 🟡 `EventBus::parallel` 注释说"Vec 与注册序对应"，实现是 JoinSet 完成序（`bus.rs:177-178 vs 199-207`）。改注释或排序。
- 🟡 `EventLog::append_batch` 跳过 Replace 区间校验（单条 append 有 `check_replace_interval`，batch 没有，`bm-kernel/src/event_log.rs:104-111`）。
- 🟡 `BranchHead.parent_branch: Option<String>` 应为 BranchId；`source_seqs: Option<Vec<u64>>` 应为 Vec<SeqNo>（typed id 的初衷）。
- 🟡 fork 分支名 = 时间戳异或（`bm-kernel/src/event_log.rs:172-175`）：同毫秒两次 fork 撞名（概率低）+ 非随机（分支 id 非秘密，仅整洁问题，换 uuid 即可）。
- 🟡 `verify_lossless` 每 append 两次序列化：大工具输出（MB 级）会放大。备注级，可只对新类型做。

### 3.6 测试与质量门

- **🔶 CI 未纳入新 crate**：`.github/workflows/release.yml` 只 `-p bm-core -p bm-server`（test 与 clippy 都如此）。内核四件套在 CI 零守卫——现在"全绿"是本地事实，不是门禁。
- **🔶 全量 `cargo test` 编译失败**：`pi_agent_rust` 的 lib test 目标缺 `tests/common/mod.rs`（os error 3）。所以"cargo test 全绿"这个说法全 workspace 不成立，质量门必须用 -p 列表。vendor 修法（加 stub 文件或禁 test target）按 pi 修补政策走 UPSTREAM_PATCHES.md 登记。
- 🟡 proptest 承诺未兑现：实现方案 §6 写"property-based（proptest）"，实际没有（vendor 里有 proptest 依赖，新 crate 没有）。
- 🟡 DualWriter 失败路径没测（测试注释自己承认"内存实现不会失败——直接验证计数正确性"）。failed 计数分支是零覆盖。
- 🟡 `dual_write_30rounds` 与 chat.rs 的"相同序列"是注释约定、非代码共享——会漂移。抽公共构造器让两边用同一函数。

### 4.3 一个语义差异要拍板：fork

三家三种 fork：**Life = 空分支**（seq 从 1 起，与我们一致）、**dsh = 带前缀种子**（fork 含 fork 点前历史）、**Hana = 物理共享前缀**（分支头回滚）。我们的空分支语义没问题（与 Life 同款），但与 A1 的动机（"回滚到旧分支/试另一条路"）之间差一步：**投影不折叠父前缀，fork 后看不到 fork 点前的历史**。parent_branch 已记录，补一个"沿 parent 链折叠前缀"的投影（或 fork 时可选 seed）即可。拍板点 4。

## 五、拍板点清单（每条：问题 / 选项 / 推荐 / 理由）

1. **阶段 1 立项顺序**
   - 选项：A. agent-loop 移植优先；B. pi-compat（QuickJS 拆出）优先
   - 推荐：**A**。理由：日志的"完整可信"是审计/Steward/分支 UI/前端投影的共同地基，越晚补越贵；两者解耦（拆法 A 是库级操作、1-2 周），pi-compat 后置不影响路线。
2. **真实验收**（10 分钟，需用户配合）
   - release 起 bm-server → 看日志"事件日志双写已启用" → 聊几轮 → sqlite3 查 `SELECT seq, session_id, type FROM event_log ORDER BY seq`。模拟验收已全绿，这一步验证"真库真链路"。
3. **事件格式版本化**
   - 选项：A. 现在给 SessionEvent 加 version 字段 + 拒绝不兼容版本（推荐）；B. 等第一次改结构时再加
   - 理由：数据量小改 schema 最便宜；dsh 的教训是"写者决定 bump（能解析 ≠ 语义正确）"。
4. **fork 语义**
   - 选项：A. 投影折叠父前缀（fork 可见 fork 点前历史，推荐）；B. fork 带种子（dsh seedLength 模式）；C. 维持空分支、分支 UI 自己拼
   - 理由：A 最贴合"回滚到旧分支"的动机，且 parent_branch 已有记录，成本最低。
5. **会话删除联动**
   - 选项：A. 删除会话时联动清 event_log（推荐）；B. 保留事件日志作可恢复"回收站"
   - 理由：用户删会话的心理预期是"数据没了"；隐私是底线（战略文档 §四·4）。
6. **Port 注册表形状**
   - 选项：A. `PortBox<T:?Sized>` 包装进 Any（推荐，零 unsafe）；B. 每 Port 一个 typed accessor（啰嗦但显式）
   - 理由：阶段 1 加 Port 时就要用，现在定避免 breaking。
7. **Loader 依赖语义**
   - 选项：A. deferred 插件（deps 未就绪先挂起、就绪再启动，dsh inject 同款，推荐）；B. 维持有序安装（manifest 顺序即拓扑）
   - 理由：应用插件依赖能力插件是常态，手工编排顺序迟早出错。
8. **质量门**
   - 选项：A. CI 纳入四新 crate（test + clippy --all-targets -D warnings）并修 vendor 缺失文件（推荐）；B. 仅本地跑
   - 理由：门禁不在 CI = 没门禁；vendor 修复按 pi 修补政策登记 P11+。
9. **全局事件游标**（跨会话事件序——Steward"全量订阅"的前置）
   - 选项：A. 现在只在契约层留口（EventQuery 加全局游标语义，推荐）；B. 不预留
   - 理由：seq 目前只有 (session,branch) 内意义，Steward（阶段 5）需要跨会话顺序；留口不动实现。
10. **前端隔离机制**（iframe/WebComponent/联邦）——**维持后拍**（阶段 4），本次不动。

## 七、阶段 1 建议范围

**主线：agent-loop 移植**（让日志从"消息面级"变"执行级"）：
1. 真序事件流（TurnStart → RequestHeader → StepStart → chunk* → AssistantMessage → ToolCall → ToolResult(output 落全) → StepEnd → TurnEnd(含 Interrupted)）；
2. 压缩事务接线（CompactionStart/Summary/End + Replace，替换现有 ctx-compactor 或先挂事件）；
3. `EventStorePort::subscribe`（replay-prefix + tail，agent-loop 读路径重做时顺手做）。

**随行小修**（§三清单，按序）：
4. 事件版本化（拍板点 3）→ 单条 append 事务化 + recover 修 head → read 单查询 + turn 计数 → PortBox → per-plugin disposer 分组 → 小一致性项（join_all/parallel 注释/batch 校验/typed id）。

**质量门**：CI 纳入四 crate（拍板点 8）。

**后置**：pi-compat（1-2 周，拆法 A 已查证）——loop 移植稳定后做，插件生态当日兼容。

**不动**：前端隔离、分支 UI、Steward、订阅推送 UI——按原路线图。
