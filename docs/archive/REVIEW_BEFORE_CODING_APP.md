## 二、编程应用 M1 差距分析（回头看核心）

M1 = 一次单任务编程：读代码 → 改 → 测 → 提交。对照现有能力：

| M1 所需 | 现状 | 差距 |
|---|---|---|
| 读代码 | read/grep/find/ls ✅ | 无 |
| 改代码 | write/edit ✅ | 无 |
| 跑测试 | bash（cargo test）✅ | 无 |
| git 提交 | bash（git）✅ | 无 |
| 会话/工具/流式 | 全链路 ✅ | 无 |
| 权限询问 | PermissionBridge ✅ | 无 |
| 子代理并行 | ✅ 已接入 | 无 |
| 断点续跑基础 | 事件日志+loop_agents 重建 ✅ | 无（M3 才验收） |

**M1 = 现有能力的编排 + 真实验收，几乎零新增代码**（最多补一个"计划模式"可选壳层体验）。

M2（活任务清单）差距：todo/write 事件协议 + 任务调整工具 + 前端任务面板——**这是真正的增量**，
也是用户痛点（"任务清单生成后不会实时插入/删除"）的核心。

M3（8h+ 长时断点续跑）：事件日志/恢复语义已在，需要心跳保持 + 跨重启 resume 打磨 + 验收。

**判断**：编程应用不是"从零造软件"，而是把已完工的运行时按编程场景编排。M1 本周可达，
M2 是主要工作量（前端面板 + 事件协议），M3 是打磨验收。迁移门槛按既定提议 = **M3**（比 ZCode
强的那一刻：8h+ 任务跨重启不丢）——M1-M2 期间可日常试用。

## 三、技术路线确认（架构 §6.8 已定调，本回看只确认执行口径）

- **寄生形态**：不自建 Agent 核心，壳 + 管家派出的编程专家树（生成权专家可递归派工）
- **复用**：bm-loop（回合）+ 内置工具集（手脚）+ 事件日志（审计/恢复）+ 前端（投影渲染）
- **M1-M2 形态建议**：先用现有聊天界面 + 新增"任务面板"（todo 事件投影），不造新壳；
  独立壳应用（文件树/编辑器/分支图）留 M3 之后——避免为 M1 造壳的浪费
- **ZCode 借鉴止于壳层**（Z1-Z7 已吸收）：计划模式/权限四级/会话恢复，按需补

## 五、风险与约束（直说）

1. **模型质量是天花板**：编程质量取决于主模型（现 MiniMax-M3）。M1 验收时若工具调用
   服从性不足（MiniMax 有飘忽史），备选 deepseek 已在 config；
2. **长时成本**：8h+ 常驻的 token 消耗靠压缩（水线 0.5 已收敛）+ 管家低成本模型（已配）；
3. **Windows 主战场**：质量门在 Windows 本地跑（方案 A），Linux/macOS 验证留三平台线；
4. **自举的鸡生蛋**：M5 自举闭环前，开发 BoenMind 仍用 ZCode——M3 迁移达成后才真正脱离。
